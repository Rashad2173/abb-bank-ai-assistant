# ABB Bank AI Assistant

A web application that answers questions about **ABB Bank** using the content of
its official website, [abb-bank.az](https://abb-bank.az). Answers are generated by
an OpenAI model with retrieval-augmented generation (RAG): relevant passages are
retrieved from a **Milvus** vector database and the model answers only from them,
citing its sources.

> Case study for ABB. The requirements and where each is met: [REQUIREMENTS.md](REQUIREMENTS.md).

## Run it

Requires Docker (with the NVIDIA runtime for the GPU; see below for CPU-only) and an OpenAI API key.

```bash
cp .env.example .env                 # put OPENAI_API_KEY into .env
docker compose up -d --build         # → http://localhost:8080
```

| Address | What |
|---------|------|
| http://localhost:8080 | the application |
| http://localhost:8001/docs … :8005/docs | Swagger UI of each service (chat, analytics, ingestion, inference, scraper) |
| http://localhost:8000 | Attu — browse the Milvus collection |

* First start: the inference service downloads its two models (~4.5 GB) into the `models` volume.
* The search index starts empty. In the app, **learn the site from its link** (or upload
  `abb_pages.jsonl`); the chat opens once the data is processed. A first crawl of the site
  takes ~30 minutes (polite: 6 parallel requests); with an existing page cache
  (`SCRAPER_DATA=./data docker compose up -d`) about 3 minutes.
* No NVIDIA GPU: `docker compose -f docker-compose.yml -f docker-compose.cpu.yml up -d --build`
  — embeddings run on the CPU and the reranker is switched off (it needs ~45 s per question
  on a CPU), so answers come from Milvus' hybrid order.

## Using the app

1. **Data** — two ways in:
   * **From the website**: enter `https://abb-bank.az`. The scraper reads every page and the
     branch/ATM network, extracts the text and indexes it, showing each stage live (pages
     found and read, documents, chunks, embeddings). Other sites are refused with a clear message.
   * **Upload a file**: `abb_pages.jsonl` produced by the scraper, or **PDF / TXT documents**
     (their text is extracted page by page). The data is kept in the browser's localStorage
     (compressed: 21 MB → 1.5 M characters).
   * **Add** keeps what is indexed and adds new / changed pages; **Replace** makes the upload
     the whole knowledge base. Only new or changed chunks are embedded either way.
2. **Chat** — answers in Azerbaijani, English or Russian with numbered sources, campaign
   status and dates; quote part of an answer to ask about it; conversations are kept in the
   sidebar. Off-topic questions, other banks, personal advice and prompt injection are refused.
3. **Dashboard** — questions per day and hour, outcomes, languages, refusal reasons, answer
   times, most cited pages and the latest questions (stored in PostgreSQL).

## How well it works

Every number below is measured; the sets and reports are in [evaluation/](evaluation/README.md).

| | Result |
|---|---|
| Scraping: CMS text of the site present in the output | **99.9 %** of 15 646 lines |
| Retrieval: the needed passage among the 10 chunks given to the model (200 questions, 2 independent sets) | **94 %** (all evidence in the top 5: 174 / 200) |
| Retrieval on 56 new questions: the source page reaches the model | **52 / 53** |
| Answers graded against the source text (56 new questions) | **54 correct + 1 partial; 0 invented facts** (the remaining miss is fixed by the current retrieval method) |
| Guardrail, independent set of 80 adversarial questions (16 injection techniques) | **80 / 80**; 0 legitimate questions refused; 0 prompt leaks |
| Answer time | ~3–7 s (search 10 ms, reranking ~1 s on a GPU, the LLM the rest) |

## Architecture

```
            ┌───────────── frontend (React, nginx) :8080 ─────────────┐
            │  /api/chat   /api/analytics   /api/ingestion   /api/scraper
            ▼                    ▼                 ▼               ▼
      chat :8001         analytics :8002    ingestion :8003   scraper :8005
   plan → search →        PostgreSQL         chunk → diff →    crawl → extract
   rerank → OpenAI →                         embed → Milvus    → ingestion
   guardrail
            │                                      │
            └──────────── inference :8004 ─────────┘     Milvus (+ etcd, MinIO)
              bge-m3 embeddings · bge-reranker-v2-m3
```

Six services talking JSON over HTTP ([services/README.md](services/README.md)). Every
service has `GET /health` and `GET /ready` (dependencies checked), carries an
`X-Request-ID` through all calls and logs, and returns errors as JSON. If the reranker is
slow or down, the chat answers from Milvus' order instead of failing.

**Retrieval** ([retrieval/README.md](retrieval/README.md)): 9 604 rule-based chunks (≤ 512
tokens, each with its page title and section path); bge-m3 dense + sparse vectors and
Milvus BM25 fused with Reciprocal Rank Fusion, the top 30 re-scored by bge-reranker-v2-m3,
10 chunks to the model. Questions in Russian or English are also searched in Azerbaijani
(some pages exist only in Azerbaijani); tender notices are searched only for procurement
questions.

**Generation**: `gpt-6-luna` with a strict JSON schema (status, refusal reason, language,
answer with `[S1]` citations). The prompts are plain files in
[services/chat/chat_service/prompts/](services/chat/chat_service/prompts/).

## Development

Python ≥ 3.12, Node 22.

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt                    # PyTorch with CUDA: see retrieval/requirements.txt
docker compose up -d milvus postgres attu              # infrastructure only
# services natively (one terminal each, see services/README.md), then the UI:
cd frontend && npm install && npm run dev              # → http://localhost:5173 (proxies /api to the services)

pytest                                                 # 236 tests
cd frontend && npm test                                # UI unit tests
python scripts/smoke_test.py                           # end-to-end check of running services
```

## Key decisions

| Decision | Reason |
|----------|--------|
| Site-specific scraper (HTML + CMS payload + the site's APIs) | A generic scraper misses tabs, accordions and the branch network; this one reaches 99.9 % of the CMS text |
| Embedding model chosen by benchmark on Azerbaijani data, on two independent question sets | One set can favour one model; bge-m3 was the most consistent, open source and free to run |
| dense + sparse + BM25, then a reranker | Each catches what the others miss (meaning, learned keywords, rare exact words like "beh"); best or equal on every measurement (report 09) |
| Models in their own inference service | Only it needs PyTorch and a GPU; the other services stay small |
| Guardrail in layers, measured, no framework | Scope rules in the same LLM call (no extra latency), citations checked in code, 80 / 80 on an independent set |
| Upload step kept, but not blocking | The brief's flow (upload → process → chat) is the first-visit path; visitors without a file can continue with the data already indexed |
| Ingestion diffs by content hash | Re-learning the site or re-uploading embeds only what changed (~seconds instead of minutes) |
| Prompts as files | Reviewable and editable without touching code |

## Known limitations

* The scraper is built for abb-bank.az; other sites are refused (other sources can be added as
  upload files, e.g. `scripts/wikipedia_to_pages.py`).
* PDF tables lose their column structure in text extraction; text-heavy PDFs work well.
* The reranker needs a GPU for interactive answers; without one the chat falls back to Milvus' order.
